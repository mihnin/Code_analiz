Как правильно подключить Xinference для анализа кода
1. Запустите модель с достаточным окном: xinference launch --model-name <имя> --context-length 32768 (или больше для файлов 1000+ строк).
2. Адрес сервера здесь должен совпадать с тем, что запустил Xinference (по умолчанию :9997).
3. Нажмите «Загрузить список» — приложение само подтянет context_length модели и выставит его в калькулятор токенов.
4. Для крупных файлов (3000+ строк) выбирайте модели с окном ≥32K и достаточным VRAM (квантизация Q4_K_M / AWQ).
5. Если запрос всё равно не проходит — смотрите лог xinference: Context length exceeded = модель загружена с меньшим n_ctx, перезапустите её с большим значением.

О приложении AI сканер

Ролевой AI-ассистент для анализа исходного кода

AI сканер — корпоративный инструмент для анализа исходного кода с помощью больших языковых моделей (LLM). Приложение работает полностью автономно, без внешних зависимостей — достаточно открыть файл в браузере.

Ключевые возможности:

  • Ролевой подход — три предустановленные роли (ИБ-специалист, Консультант, Разработчик), каждая со своим набором специализированных промптов
  • Мультиязычность кода — поддержка ABAP, 1С, Python, JavaScript с учётом специфики каждого языка в промптах
  • Гибкость подключения — облачный API (DeepSeek) или локальные модели (LM Studio, Ollama, Xinference)
  • Потоковая генерация — ответы выводятся в реальном времени по мере генерации
  • Контроль бюджета токенов — визуальный счётчик помогает не превысить контекстное окно модели
  • Расширяемость — вы можете добавлять собственные промпты через матрицу в настройках

Роли и их назначение

Три специализированные роли для разных задач

Информационная безопасность

Роль для специалистов по ИБ, отделов безопасности и аудиторов.

Доступные действия:

  • Анализ уязвимостей — поиск уязвимостей по методологии OWASP Top 10, определение CWE-типов, оценка критичности
  • Аудит безопасности — комплексная проверка: аутентификация, криптография, управление данными, конфигурация

Пример использования: Перед выводом модуля в продуктив, ИБ-специалист вставляет код и получает отчёт о потенциальных уязвимостях с рекомендациями по исправлению.

Консультант

Роль для бизнес-аналитиков, системных аналитиков и консультантов.

Доступные действия:

  • Объяснить логику — перевод кода на понятный бизнес-язык, описание входов/выходов, бизнес-правил
  • ТЗ на доработку — автоматическая генерация ТЗ для модификации существующего кода
  • ТЗ с нуля — создание полноценного технического задания на основе анализа кода

Пример использования: Консультант получает код от заказчика, вставляет его в приложение и получает описание бизнес-логики на понятном языке или готовый шаблон ТЗ.

Разработчик

Роль для разработчиков, тимлидов и архитекторов.

Доступные действия:

  • Рефакторинг — анализ code smells, предложения по улучшению, переписанный код с применением SOLID/DRY/KISS
  • Оценка качества (1-5) — детальная оценка по 5 критериям: читаемость, архитектура, надёжность, производительность, поддерживаемость
  • Анализ производительности — поиск узких мест, оценка алгоритмической сложности, рекомендации по оптимизации

Пример использования: Разработчик перед код-ревью вставляет свой код и получает автоматическую оценку качества и предложения по рефакторингу.

Руководство по ИБ-анализу кода

Пошаговая инструкция: как проверять код на уязвимости

Принцип работы: «Никому не доверяй, всё проверяй»

ИБ-анализ построен на принципе Zero Trust: каждая строка кода рассматривается как потенциальный вектор атаки. AI не верит комментариям разработчика — он проверяет фактический код. Каждый параметр, каждый ввод пользователя, каждый вызов API считается «заражённым» (tainted) до явной проверки.

Шаг 1. Выбор роли

В боковой панели нажмите «Информационная безопасность» (иконка щита). Эта роль активирует набор специализированных промптов для поиска уязвимостей.

Шаг 2. Выбор языка программирования

Выберите язык анализируемого кода. Это критически важный шаг — от него зависит, какие специализированные проверки будут выполнены:

Язык Специализированный промпт Что проверяет дополнительно
Python ИБ-анализ Python eval/exec, pickle, subprocess+shell, yaml.load, SSTI, Flask debug
ABAP ИБ-анализ ABAP AUTHORITY-CHECK (4 паттерна обхода), динамические CALL, Open SQL, S_TCODE/S_DATASET
1С ИБ-анализ 1С Выполнить/Вычислить, COM-объекты, привилегированный режим, внешние обработки .epf
JavaScript Общие промпты (Анализ уязвимостей) eval, innerHTML, prototype pollution, SSRF, XSS, ReDoS

Шаг 3. Выбор действия (промпта)

После выбора языка в панели действий появятся кнопки. Для ИБ-анализа доступны:

1

Анализ уязвимостей (универсальный)

Доступен для всех языков. Многослойный анализ по OWASP Top 10, CWE/SANS Top 25 с Taint Analysis. Ищет инъекции (SQL, OS, код), захардкоженные секреты, слабую криптографию, проблемы SSL/TLS, веб-уязвимости (XSS, CSRF, SSRF), path traversal, десериализацию, утечку информации. Выдаёт оценку 1-10.

2

Аудит безопасности (универсальный)

Доступен для всех языков. Комплексная проверка по 7 направлениям: аутентификация, управление секретами, защита данных, входные данные, веб-безопасность, утечка информации, обработка ошибок. Формат: compliance-отчёт со статусами ✅/⚠️/❌ и оценкой соответствия.

3

ИБ-анализ [Язык] (специализированный)

Появляется только при выборе соответствующего языка. Содержит десятки языко-специфичных паттернов уязвимостей. Даёт максимально глубокий анализ для конкретного языка.

Рекомендация: Для максимального покрытия используйте специализированный промпт (ИБ-анализ Python / ABAP / 1С). Если нужен быстрый общий обзор — используйте «Анализ уязвимостей». Для формального отчёта — «Аудит безопасности».

Шаг 4. Вставьте код и запустите

Вставьте код в поле ввода (или прикрепите файл через кнопку «Файл контекста»), затем нажмите Ctrl+Enter или кнопку «Анализировать».

Пример: анализ ABAP-кода

Настройки

Роль: Информационная безопасность → Язык: ABAP → Действие: ИБ-анализ ABAP

Что будет проверено (8 категорий):

# Категория Что ищет Пример уязвимого кода
1 Обход авторизации Нет AUTHORITY-CHECK, игнорирование SY-SUBRC, DUMMY в полях, * во всех полях AUTHORITY-CHECK... без IF SY-SUBRC <> 0
2 SQL-инъекции Динамический Open SQL, конкатенация WHERE, Native SQL SELECT * FROM (lv_tab) WHERE (lv_where)
3 Динамические вызовы CALL FUNCTION/METHOD из переменной, GENERATE SUBROUTINE POOL, INSERT REPORT CALL FUNCTION lv_func_name
4 Секреты в коде Пароли в CONSTANTS/переменных, RFC-credentials CONSTANTS: c_pass VALUE 'admin123'
5 Работа с файлами OPEN DATASET без S_DATASET, path traversal OPEN DATASET lv_user_path
6 Утечка информации WRITE/MESSAGE с техническими деталями, дампы ST22 MESSAGE lv_sql_error TYPE 'E'
7 DoS-векторы SELECT * без UP TO n ROWS, FOR ALL ENTRIES с пустой таблицей SELECT * FROM big_table
8 RFC-интерфейсы Нет S_RFC, передача данных без шифрования, BAPI без проверки CALL FUNCTION ... DESTINATION без S_RFC

Особое внимание: 4 паттерна обхода AUTHORITY-CHECK

Паттерн Проблема Последствие
Полное отсутствие SELECT/UPDATE/DELETE без AUTHORITY-CHECK Любой пользователь читает/меняет данные
Игнорирование SY-SUBRC AUTHORITY-CHECK есть, но нет IF SY-SUBRC <> 0 Проверка бесполезна — код продолжает выполняться
DUMMY в полях ID 'ACTVT' DUMMY Фиктивная проверка — пропускает любой доступ
* во всех полях FIELD '*' для каждого ID Проверяется наличие любого полномочия, а не конкретного

Результат: отчёт с привязкой к SAP-объектам авторизации (S_TCODE, S_DATASET, S_RFC, S_DEVELOP), приоритетами исправления и примерами безопасного ABAP-кода.

Для 1С: основные проверки

При выборе языка 1С и действия «ИБ-анализ 1С» проверяются 10 категорий, включая:

  • Выполнить/Вычислить — выполнение произвольного кода из строковых переменных
  • COM-объекты — WScript.Shell (RCE!), FileSystemObject (доступ к файлам), ADODB.Connection (обход платформы к БД)
  • Привилегированный режим — УстановитьПривилегированныйРежим(Истина) без ограничения области и без try-except
  • Внешние обработки — ВнешняяОбработка.Создать() без проверки цифровой подписи
  • HTTP без SSL — HTTPСоединение на порт 80, отключённая проверка сертификата
  • Серверные методы — экспортные процедуры &НаСервереБезКонтекста без проверки ПравоДоступа()

Что значит «thinking-модель» на практике?

Когда вы используете deepseek-reasoner (или другую рассуждающую модель — Qwen3, QwQ), происходит следующее:

  • Фаза 1 — «Рассуждение» (5-30 секунд): модель «думает» — анализирует код, прослеживает потоки данных, перебирает возможные атаки. Вы видите пульсирующую иконку мозга и текст «Ожидание ответа модели...»
  • Фаза 2 — «Ответ»: модель выдаёт финальный структурированный отчёт. Над ответом появляется сворачиваемая секция «Рассуждения» (фиолетовая) — можно раскрыть и посмотреть, как модель пришла к выводам
  • Бейдж: после завершения рядом с ответом отображается «С рассуждениями (~N токенов)» — это токены, потраченные на «мышление» (они не видны в основном ответе, но расходуют бюджет контекстного окна)

Рассуждающие модели тратят больше токенов и времени, но находят значительно больше уязвимостей, особенно неочевидных: timing-атаки, TOCTOU, сложные цепочки инъекций.

Альтернатива: deepseek-chat (быстрая модель)

Если вам нужен быстрый предварительный скан (1-3 секунды вместо 10-30), используйте deepseek-chat. Она хорошо находит очевидные проблемы (SQL-инъекции, захардкоженные пароли, eval), но может пропустить тонкие уязвимости. Для deepseek-chat температура 0.1-0.2 работает в полную силу.

Файл инструкций (опционально, но рекомендуется)

Вы можете прикрепить к промпту файл с корпоративными стандартами ИБ — он будет встроен в системный промпт и модель будет проверять код на соответствие вашим внутренним политикам. Как это сделать:

  • Перейдите в Настройки → Матрица промптов
  • Найдите нужный промпт (например, «ИБ-анализ Python») и нажмите «Редактировать»
  • В модальном окне нажмите «Загрузить файл инструкций»
  • Выберите .txt или .md файл с вашими стандартами (например, «Политика безопасной разработки», «Требования к ABAP-коду», «Чек-лист ИБ для 1С»)
  • Файл сохранится с промптом и будет автоматически добавляться в каждый запрос к AI
Важно: AI-анализ — это первая линия проверки, а не замена ручного аудита. Используйте результаты как чек-лист для более глубокого анализа. Критичные уязвимости (🔴 Critical) всегда верифицируйте вручную. Рассуждающие модели (deepseek-reasoner) дают значительно более глубокий анализ, но стоят ~4x дороже по токенам.

Модели: качество, рассуждения, выбор

Как выбор модели влияет на результат

Качество ответов зависит от модели

Самый главный фактор, влияющий на качество анализа — выбранная модель. Более мощные модели лучше понимают код, находят больше проблем и дают более точные рекомендации. Не все модели одинаково хорошо работают с разными языками программирования.

Модели с рассуждением vs обычные

Быстрая

Стандартные модели

Например: deepseek-chat

  • Быстрый отклик (1-3 сек)
  • Подходит для простых задач
  • Хорошо работает с объяснением кода
  • Менее затратна по токенам
  • Рекомендуется для большинства задач
Рассуждающая

Модели с Chain-of-Thought

Например: deepseek-reasoner

  • Медленнее (5-15 сек), но глубже
  • Лучше для сложного анализа
  • Находит неочевидные уязвимости
  • Расходует больше токенов
  • Рекомендуется для ИБ-аудита

Облако vs Локальные модели

Облачный API (DeepSeek) — высокое качество, стабильная работа, требуется API-ключ и подключение к интернету. Данные отправляются на сервер провайдера.

Локальные модели (LM Studio / Ollama / Xinference) — данные не покидают вашу машину, полная конфиденциальность. Качество зависит от размера модели и мощности оборудования. Для корпоративного анализа рекомендуются модели от 13B параметров.

CLI-инструмент, лёгкий

  • Управление через терминал
  • Простая установка моделей

  • Контекст: ollama show модель

Xinference

Платформа инференса (Xorbits)

  • Корпоративное развёртывание
Совет: Если работаете с конфиденциальным кодом — используйте локальные модели. Для максимального качества анализа — облачные API с мощными моделями.

Токены и контекстное окно

Как работает подсчёт токенов в приложении

Что такое токены?

Токен — это минимальная единица текста для LLM-модели. Это не символ и не слово, а что-то среднее: часть слова, слово целиком или знак пунктуации. Модели «думают» токенами, и у каждой модели есть лимит на их количество.

Латиница / код: ~4 символа = 1 токен function = ~2 токена
Кириллица: ~2 символа = 1 токен Проверка = ~4 токена

Контекстное окно

Контекстное окно — это максимальное количество токенов, которое модель может обработать за один запрос. Сюда входит всё: и ваш код, и промпт, и история чата, и ответ модели.

Как читать шкалу токенов

В нижней части панели кода отображается цветная шкала бюджета токенов:

Фиолетовый — системный промпт (инструкция для AI)
Синий — ваш код или текст
Жёлтый — прикреплённый файл контекста
Бирюзовый — история переписки с AI
Серый — зарезервировано для ответа модели

Длина чата и контекстное окно

При каждом уточняющем вопросе вся предыдущая переписка повторно отправляется модели — так устроен протокол OpenAI Chat API. Это значит:

  • Чем длиннее диалог, тем больше токенов расходуется на историю
  • При превышении контекстного окна шкала становится красной — дальнейшие вопросы могут быть обрезаны или вызвать ошибку
  • Когда шкала жёлтая (>80%) — рекомендуется начать новый чат
  • Для длинных диалогов выбирайте модели с большим контекстным окном (64K-128K)
Совет: Нажмите на область токенов в панели кода, чтобы увидеть детальную разбивку по компонентам. Если шкала заполнена — очистите чат и начните новый анализ.

Как писать промпты

Руководство по созданию и редактированию промптов

Зачем нужны пользовательские промпты?

AI сканер поставляется с 8 предустановленными промптами, но вы можете добавить собственные через Настройки → Матрица промптов → Добавить. Это позволяет адаптировать приложение под специфику вашей организации.

Структура хорошего промпта

1

Роль и экспертиза

Начните с определения роли AI: кто он, какой у него опыт, в чём его экспертиза.

Ты — эксперт по информационной безопасности SAP с 10-летним опытом аудита ABAP-кода.
2

Задача

Чётко опишите, что именно нужно сделать с предоставленным кодом.

Проведи анализ данного кода на соответствие стандартам безопасной разработки компании.
3

Формат ответа

Укажите желаемую структуру ответа — заголовки, списки, таблицы, оценки.

Для каждой проблемы укажи: Тип, Критичность (1-5), Строка кода, Рекомендация.
4

Специфика языка

Добавьте конкретные указания для целевых языков программирования.

Для ABAP: проверь AUTHORITY-CHECK, динамические вызовы, захардкоженные учётные данные.

Примеры кастомных промптов

Проверка на соответствие стандартам компании

Роль: infosec

Ты — внутренний аудитор кода компании. Проверь код на соответствие корпоративным стандартам:
1. Именование переменных (венгерская нотация для ABAP)
2. Обязательные комментарии к функциям
3. Обработка исключений в каждом блоке
4. Логирование операций с БД
Формат: таблица [Правило | Статус | Комментарий]

Генерация unit-тестов

Роль: developer

Ты — QA-инженер. Проанализируй код и сгенерируй набор unit-тестов.
Для каждого метода/функции создай тесты:
1. Позитивный сценарий (ожидаемый ввод)
2. Негативный сценарий (невалидный ввод)
3. Граничные значения
Используй формат тестового фреймворка, подходящий языку.
Совет: Чем конкретнее промпт — тем лучше результат. Указывайте формат вывода, критерии оценки, специфику языка. Избегайте расплывчатых формулировок типа «проанализируй всё».

Настройки приложения

Описание параметров генерации и рекомендации

Параметры генерации

Контекстное окно

По умолчанию: 64K

Максимальный объём текста (в токенах), который модель может обработать за один запрос. Включает всё: системный промпт, ваш код/текст, прикреплённые файлы, историю чата и ответ модели.

Зачем это нужно? Этот параметр управляет калькулятором токенов — цветной шкалой в нижней части панели кода на главном экране. Калькулятор показывает, сколько токенов занято и сколько осталось для ответа. Если значение не совпадает с реальным окном вашей модели — шкала будет показывать неверные данные.

4K — маленькие локальные модели (1-3B параметров) 8K — стандарт для большинства локальных моделей (по умолчанию при выборе локального режима) 16-32K — продвинутые локальные модели с расширенным контекстом 64K — облачные API (по умолчанию при выборе облачного режима) 128-256K — модели с очень большим окном, для длинных диалогов и больших файлов
Для локальных моделей: при загрузке списка моделей приложение попытается определить размер контекстного окна автоматически. Если это не удалось — выставьте значение вручную, ориентируясь на настройки вашего сервера. Как узнать реальный размер: в LM Studio — вкладка модели → Context Length; в Ollama — ollama show имя_модели; в Xinference — веб-интерфейс → параметры модели. Если поставить больше, чем поддерживает модель — запросы будут обрезаны или вызовут ошибку. Если меньше — шкала токенов будет преждевременно показывать «переполнение».

Макс. токенов ответа

По умолчанию: 4096

Максимальная длина ответа модели. Если ответ сложный и длинный, модель остановится при достижении этого лимита.

256-1024 — для коротких ответов (оценка качества, краткое описание) 2048-4096 — для стандартного анализа (рекомендуется) 8192-16384 — для длинных ответов (полный рефакторинг, подробное ТЗ)

Учтите: токены ответа «отъедают» бюджет контекстного окна. Если ставите 16384 при окне 64K — на ввод останется только 48K.

Температура

По умолчанию: 0.3

Контролирует «креативность» модели. Низкая температура — модель выбирает наиболее вероятные ответы (точнее). Высокая — более разнообразные и нестандартные.

0 — 0.3 — точный, детерминированный анализ (рекомендуется для кода) 0.5 — 0.7 — баланс точности и креативности 1.0 — 2.0 — креативные задачи (не рекомендуется для анализа кода)

Для анализа кода, аудита безопасности и рефакторинга используйте 0.1 — 0.3. Для генерации ТЗ и описаний можно поднять до 0.5.

Прочие настройки

  • Среда выполнения — переключение между облачным API (DeepSeek) и локальными моделями (LM Studio / Ollama / Xinference)
  • API ключ — секретный ключ для доступа к облачному API. Хранится только в localStorage вашего браузера
